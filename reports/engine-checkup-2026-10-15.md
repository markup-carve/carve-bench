# Engine checkup, 2026-10-15

These samples compare the pinned engines with commits taken from each engine's merged `main`. The host was shared and had 16 logical CPUs. The [raw samples and provenance](data/engine-checkup-2026-10-15) record observations, with commit IDs and run settings in `provenance.json`. On 2026-10-15, the PHP phase and memory probes finished at 16:47 and 16:48 CEST, the paired wall run at 17:21 CEST, the CPU run at 17:53 CEST, and the Rust allocation probe at 18:05 CEST. The PHP memory probe used `php -n` with `ctype` and `mbstring` enabled, so JIT and opcache were off. The one-off runner scripts remained local; the archived samples and fixture bases support review but do not reproduce the runs by themselves.

## Revisions and inputs

Node was 22.22.2, PHP was 8.5.11, and rustc was 1.97.1. The comparison input is `corpus/small.crv` (1,233 bytes, SHA-256 `e59b53242d55149997deab060fe0fb326b9dfaa5548b4c1f600a4c1daff4dec3`). Medium and large join 50 and 400 copies with one newline between copies, giving 61,699 and 493,599 bytes. The AST variant adds one 45-byte footnote to those inputs, giving 61,744 and 493,644 bytes; [ast-base.crv](data/engine-checkup-2026-10-15/ast-base.crv) shows the small version. The comparison input contains an image and a cross-reference, which sends JavaScript through its AST route. The older benchmark name `core` does not describe its route.

Fresh processes warmed each engine, then ran alternating pin/main pairs. The wall run used two ABBA rounds; its runner settings recorded PHP JIT as enabled. The JS and Rust CPU run used four ABBA rounds. The separate PHP phase run used two reversed rounds with JIT off. It finished less than a minute after a corrected PHP scaling suite; its start time was not retained, so overlap and residual host contention cannot be ruled out. The CPU run began with a 1-minute host load average of 30.7, and the wall run began at 10.9. The CPU runner did not record its start time or whether performance suites overlapped, so contention cannot be ruled out. Ratios near 10% are uncertain on this host. The [output hashes](data/engine-checkup-2026-10-15/output-hashes.json) show that the September mixed corpus produced different output between the pin and main in all three engines, so its time ratios do not compare equivalent work. The memory and allocation probes took one sample per depth and phase.

## Findings

JavaScript's measured main took 1.20 times the pin's CPU time on the medium comparison input, with all eight main samples above all eight pin samples. The large comparison input had a 1.23 CPU median ratio but wide overlap; the AST variant's medium CPU ratio was 1.00. Wall ratios were 1.29 on comparison medium, 0.92 on comparison large, and 1.20 on AST-variant medium. A later code investigation found two full-tree hydration passes for empty references in the renderer. [The renderer fix](https://github.com/markup-carve/carve-js/pull/3172) has since merged. The paired CPU samples here predate that fix.

After the fix merged, a render-only rerun used JS main `51996af1540b76ced08536a7bd1e473d48e01096`. That main also contains other changes since the first measured main, so this rerun does not isolate the fix's effect. On the 61,699-byte input, median CPU time was 7.11 ms/op at the pin and 6.63 at merged main. The 493,599-byte input measured 82.01 and 80.67 ms/op, with heavily overlapping samples. The render-only runner called `renderHtml(parse(source))` on an unresolved parse tree; `carveToHtml(source)` also resolves references and applies transforms. Their outputs were 143,069 and 150,950 bytes, so the render-only times describe a separate API path. The [CPU profile summary](data/engine-checkup-2026-10-15/js-merged-profiles.json) covers inline scanning, list parsing, `attachBlockPos` source mapping, document-ID visitation, and `collectLinkDefs`. These profiles cover different phases, not a matched pin/main HTML pair; sample counts are statistical and include module startup. A separate [V8 allocation trace](data/engine-checkup-2026-10-15/js-merged-allocation.json) counted 754.7 MB in GC intervals at the pin and 698.9 MB at merged main over 20 warmed medium HTML operations. It omits allocations after the last GC, so these are lower bounds, not exact totals.

The [merged-main combined HTML rerun](data/engine-checkup-2026-10-15/js-merged-html.json) used three ABBA rounds and began at a 1-minute host load of 12.4. Median CPU times in ms/op were 5.75 versus 5.79 at small size, 70.66 versus 73.51 at medium, and 509.19 versus 488.93 at large, pin versus merged main. The AST-variant medium and large inputs measured 62.77 versus 60.85 and 625.71 versus 623.79. All five ratios were within about 4% of the pin on this run. The pin itself measured 55.57 ms/op on medium in the earlier CPU run and 70.66 here, so the two runs cannot isolate the renderer fix.

PHP's fixed-input AST wall ratios were 1.05 at medium size and 0.97 at large size. The comparison input's large wall ratio was 1.12, with high sample spread. Its no-JIT phase wall-time medians ranged from 0.88 to 1.09 times the pin across brackets, partial brackets, lists, quotes, and paragraphs. The depth-192 list parse peak rose from 3,924,712 to 4,929,144 bytes above start, while retained memory fell from 228,648 to 183,080 bytes. The depth-192 quote parse peak rose from 1,910,184 to 2,172,328 bytes. Both were transient parser memory increases. Depth-192 quote and list render peak memory matched at pin and main: 263,864 and 788,152 bytes above start, respectively. Both the [pin renderer](https://github.com/markup-carve/carve-php/blob/29e428174d9c5c61fcb5649f156568152db159d4/src/Renderer/HtmlRenderer.php) and [measured-main renderer](https://github.com/markup-carve/carve-php/blob/c7886ac5311b42a5ea81f9ecaeb131270e005b61/src/Renderer/HtmlRenderer.php) group nested quote and list chains.

The [list parser fix](https://github.com/markup-carve/carve-php/pull/3485) merged at `0309966a67954a6cb6227c9c416f5501ce5559ed`. A [fresh merged-main memory probe](data/engine-checkup-2026-10-15/php-merged-memory.json) measured 3,094,136 bytes above start for depth-192 list parsing, below the pin’s 3,924,712 bytes. In the [paired phase rerun](data/engine-checkup-2026-10-15/php-merged-phases.json), pooled CPU sample medians for list parse, render, and combined HTML were 1.08, 1.05, and 1.06 times the pin. Quote parse measured 1.15, while quote render and combined HTML measured 0.99 and 1.05. Two reversed rounds do not establish a stable quote CPU regression. These are observations of the merged revision, which includes changes beyond the list fix.

The [quote parser fix](https://github.com/markup-carve/carve-php/pull/3487) then merged at `9eb33ad2ebf16a8f14a6252b30d2b3190fda3739`. A [fresh probe of that merged commit](data/engine-checkup-2026-10-15/php-merged-quote-memory.json) measured depth-192 quote parse at 1,897,896 bytes above start, below the pin’s 1,910,184. Its list parse peak remained 3,094,136 bytes, also below the pin. Retained memory and output hashes matched the earlier probe. In the [paired phase rerun](data/engine-checkup-2026-10-15/php-merged-quote-phases.json), pooled CPU sample medians for quote parse and render were 1.03 and 1.01 times the pin; combined HTML was 1.05. List parse, render, and combined HTML ratios were 1.05, 1.00, and 1.03. These two-round timing differences are too small for a regression claim on the shared host. The [quote-fix PR](https://github.com/markup-carve/carve-php/pull/3487) passed its PHP 8.2, PHP 8.5, and coding-standard checks before merge.

Rust's medium comparison input measured 7.77 ms/op at pin and 7.92 ms/op at main in CPU time. Large measured 87.26 and 87.18 ms/op. The AST-variant medium input measured 10.98 and 12.13 ms/op, but that row had a much wider sample spread than the comparison input. The comparison input's wall ratios were 1.11 at medium and 1.08 at large size; those differences did not recur in the paired CPU run. At quote depths 64, 128, and 192, render allocation counts were 12, 13, and 14 at both revisions. Depth-192 quote rendering requested 300,639 bytes for 78,158 output bytes at both revisions. List render allocation counts were 15, 16, and 16; depth-192 requested bytes were 601,703 for 297,607 output bytes at both revisions. Parse allocation counts matched. Depth-192 parse requests rose by 2.0% for quotes and 0.9% for lists. The [quote renderer](https://github.com/markup-carve/carve-rs/blob/7d2fd546e2d9cb484fda3d365348317c0f3d293b/src/render.rs) writes into the caller's `String`.

An initial PHP scaling attempt was invalid because its symlinked Composer vendor directory loaded classes from a different checkout; after reinstalling dependencies in the measured checkout, the recorded run passed. The completed scaling suites passed on the tested mains: [JavaScript](data/engine-checkup-2026-10-15/js-perf-tests.txt) 108 selected performance tests, [PHP](data/engine-checkup-2026-10-15/php-scaling-tests.txt) 219 tests with 48,066 assertions, and [Rust](data/engine-checkup-2026-10-15/rust-perf-tests.txt) 105 isolated guards. The first measured JavaScript main had a higher medium comparison-input CPU median than the pin. The later merged-main run did not retain that gap, though different pin times across sessions prevent attributing the change to one commit. The paired runs do not establish a Rust CPU or render-allocation regression. Both PHP parser peaks seen at the first measured main fell below the pin in fresh probes of the later merged fixes.
